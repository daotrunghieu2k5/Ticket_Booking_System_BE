2. US-14 Business Rules
Booking

Booking phải ở:

WAITING_PAYMENT

mới được phép tạo payment.

Flow:

Booking WAITING_PAYMENT
        ↓
Payment PENDING
        ↓
Create PaymentTransaction PENDING
        ↓
Call PayOS
        ↓
checkoutUrl
        ↓
User thanh toán
        ↓
PayOS Webhook
        ↓
PaymentTransaction SUCCESS
Payment SUCCESS
Booking PAID
SeatHold deleted

Nếu payment attempt thất bại:

PaymentTransaction FAILED
Payment vẫn PENDING
Booking vẫn WAITING_PAYMENT

để user có thể retry.

3. Payment Retry

Mỗi lần:

POST /api/v1/payments/{bookingId}

khi Payment vẫn PENDING:

LUÔN tạo PaymentTransaction mới.

Không reuse transaction cũ.

Ví dụ:

Transaction #101 → FAILED
Transaction #102 → PENDING
Transaction #103 → PENDING

Đây là behavior hợp lệ.

Mỗi transaction mới phải có:

orderCode = PaymentTransaction.id

Không generate UUID cho orderCode.

12. PaymentService

Tạo:

PaymentService
PaymentServiceImpl

Endpoints logic:

createPayment
getPaymentById
getPaymentByBookingId
createPayment

Flow chính:

1. Load Booking
2. Nếu không tồn tại → 404
3. Check ownership
4. Nếu không phải owner → 403
5. Check Booking.status == WAITING_PAYMENT
6. Nếu không → 400
7. Load Payment
8. Check Payment.status
9. Nếu SUCCESS → ConflictException / 400 theo exception mapping hiện tại
10. Tạo PaymentTransaction mới PENDING
11. Commit transaction local
12. Gọi PayOS ngoài DB transaction
13. Nhận checkoutUrl/paymentLinkId
14. Transaction DB thứ hai
15. Update PaymentTransaction
16. Return checkoutUrl
13. CỰC KỲ QUAN TRỌNG — Transaction Split

Không được viết:

@Transactional
public PaymentLinkResponse createPayment(...) {
    ...
    payOS.createPaymentLink(...);
    ...
}

Cách này không được phép.

Phải sử dụng:

Transaction 1
    ↓
create PaymentTransaction
    ↓
COMMIT


External PayOS API
    ↓


Transaction 2
    ↓
update PaymentTransaction
    ↓
COMMIT

Dùng:

PaymentLocalTransactionService

để tránh self-invocation của Spring AOP.

Ví dụ architecture:

PaymentServiceImpl
        |
        +--> PaymentLocalTransactionService
        |       |

16. Webhook Processing

Webhook flow phải chính xác như sau:

Step 1 — Verify signature

Nếu signature invalid:

log warning
không update DB
return HTTP 200

Không được cập nhật Payment/Booking.

Step 2 — Find transaction

Lấy:

orderCode

Sau đó:

transactionCode = String.valueOf(orderCode)

Lookup:

PaymentTransaction

Nếu không tìm thấy:

log warning
return 200

Không throw 404 ra PayOS.

Step 3 — Idempotency

Nếu:

PaymentTransaction.status != PENDING

thì:

return 200

Không xử lý lại.

17. Concurrent Payment Transactions

Đây là phần bắt buộc.

Có thể xảy ra:

Transaction A = PENDING
Transaction B = PENDING

và B SUCCESS trước.

Khi webhook B SUCCESS:

Transaction B = SUCCESS
Payment = SUCCESS
Booking = PAID
SeatHold = DELETE

Sau đó webhook A SUCCESS đến.

Lúc này:

Payment.status == SUCCESS

Do đó:

Transaction A = SUCCESS

nhưng:

KHÔNG được:
- update Booking lần nữa
- delete SeatHold lần nữa
- thực hiện business success flow lần nữa

Chỉ cập nhật transaction A và kết thúc.

18. Webhook SUCCESS

Nếu Payment chưa SUCCESS:

PaymentTransaction = SUCCESS
Payment = SUCCESS
Booking = PAID

Sau đó cleanup SeatHold.

SeatHold phải được tìm chính xác theo:

userId
eventSessionId
seatIds từ BookingItems

Sau đó DELETE.

Không xóa SeatHold của user khác.

Không xóa SeatHold của seat khác.

19. Webhook FAILED

Nếu PayOS báo FAILED:

PaymentTransaction = FAILED

Nhưng:

Payment = PENDING
Booking = WAITING_PAYMENT

Không chuyển Payment thành FAILED.

Lý do:

user có thể retry payment

Đây là business rule bắt buộc.
